# LC04-S2 — QR-bound HPKE feasibility laboratory (not a secure phone feature)

## What was implemented

An isolated JVM research module based on **Google Tink 1.23.0**, using **RFC 9180 HPKE**, X25519/HKDF-SHA256/AES-256-GCM. The module uses Tink's own HybridEncrypt/HybridDecrypt primitives, not hand-written elliptic-curve, HKDF or AEAD implementations.

- Ephemeral in-memory receiver keyset, exporting an in-memory **public** keyset to a JVM-only phone simulator. This is **not yet a compact, authenticated QR wire format**.
- TV invitation and pairing IDs, direction, operation and monotonic counter included in Tink's authenticated HPKE **context info**. Mismatch -> decrypt failure.
- Maximum 4096-byte plaintext, 5120-byte ciphertext, <=128 messages and strict increasing counters; replay and oversized messages rejected.
- JVM unit tests prove confidentiality/tamper/context handling, key mismatch, replay/operation substitution, and secret-safe textual representations.
- **Deliberate counterexample test:** *anyone* who knows the TV public key and binding identifiers can encrypt a message the TV decrypts. HPKE base-mode encryption is **not** sender authentication.
- One-time consumption of plaintext with zeroing of temporary arrays. JVM GC still prevents a formal guarantee of full memory eradication.

## Hard nonclaims

This experiment does **not** provide:
1. An independently authenticated **HTTPS phone page**. The current TV-hosted `http://<private IP>/pair.js` can be rewritten by an on-path LAN attacker. As a result, **no provider credentials can be safely entered into that page**, even if this HPKE lab were called.
2. Secure binding between TV confirmation and a sender device/public key. Current `PairingAuthority` authorizes a bearer, but the bearer is exchanged over plaintext HTTP, so possession cannot prove legitimate phone identity to a LAN attacker.
3. Mutual authentication, forward-secure two-way channel, browser WebCrypto compatibility, authenticated responses, or protection against a legitimate device's compromise.
4. A safe public API endpoint; lab has no dependency from `:app:tv`, `:local-control:server` or `:local-control:onboarding`. No HTTP source API added.
5. Tested compatibility with the supported Android TV API26 crypto provider. Java host tests do not validate target Android runtime, nor the target phone browsers.
6. Production readiness or approval to merge source credential input.

The basic encryption context is application-specific **associated context**, not proof of sender identity. Changing fields is cryptographically detected only when their correct values are already authenticated elsewhere. No custom key exchange or ad hoc home-grown replacement for TLS has been shipped.

## Browser/transport decision gates

| Candidate | Authenticated UI | LAN access | Main limitation | Gate |
|---|---|---|---|---|
| Public HTTPS static frontend + local HTTP with *separate E2EE* | HTTPS | Chrome Local Network Access permission with `targetAddressSpace:local`; browser differences | Must authenticate TV key from physical QR, the sender from approved phone key and E2EE responses; no internet offline | NOT ACCEPTED |
| HTTPS/HTTP3 WebTransport certificate hashes | HTTPS | LNA permission | Requires QUIC HTTP/3 server and browser support; current Ktor CIO is not WebTransport | NOT ACCEPTED |
| Native phone companion + QR key pinning | Signed application package | Native LAN sockets | Installation, Android and iOS application coverage | NOT ACCEPTED |
| Plain private-LAN HTTP | NO | Existing Ktor CIO | MITM can steal bearer or replace JS | REJECTED for credentials |

The Google Chrome LNA specification explicitly requires an HTTPS source context for local-network access, with the usual user prompt. Browser compatibility and offline requirements must be measured, not presumed. Browser CORS permission cannot substitute for E2EE or TV identity verification.

## Acceptance protocol for the next slice (S2-B)

1. Choose the product-supported frontend trust root: a pinned static HTTPS origin with an immutable deployable asset or a signed native phone app; do not fall back to untrusted LAN JavaScript.
2. Create an actual QR-encoded authenticated TV public key and sender enrollment bound to a TV-displayed human confirmation code. The LC01 bearer alone must not grant provider rights.
3. Add one authenticated **bidirectional** transcript per paired device with HKDF/AEAD domain separation (or a reviewed high-level Noise/TLS protocol), message sequence and replay limits. Prefer audited libraries.
4. Implement hostile MITM tests: substituted HTML/JS, replaced QR key, phone public key spoofing, downgraded origin, replay, concurrent revocation, Android network changes, and response spoofing.
5. Run real target browser/Android version compatibility, TV API26/API36 and D-pad tests. A compatibility failure must yield a visible fallback, **never silent plaintext downgrade**.
6. Only after evidence can a trusted transport create/accept the internally guarded `ProtectedSourcePrincipal` and expose M3U/Xtream, invoking the existing `SourceOnboarding` adapter.
